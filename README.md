# Xeon V3 Control 2
Windows App SDK / WinUI 3, .NET 10, Windows 11 x64. Новый проект расположен отдельно от XeonV3Control.

**Официально поддерживаемая платформа: LGA2011-3 / X99.** На других платах анализ файлов может работать; совместимость не гарантируется. Поддержка платформы не означает, что любая конфигурация защиты Windows разрешит драйвер.

## Выбор источника
- **Файл BIOS / пакет производителя**: на странице нет отдельного селектора типа файла; после нажатия «Выбрать файл» стандартный Windows Shell file-open dialog содержит системный список «Тип файла» с фильтрами «Все поддерживаемые файлы», «Образы BIOS», «Архивы» и «Пакеты производителя». Для именованных фильтров используется managed COM projection `IFileDialog.SetFileTypes`; `P/Invoke`, native helper и firmware-tool для picker не используются. Диалог принимает обычные образы (`.bin`, `.rom`, `.fd`, `.cap`, `.bio`, `.bios`, `.img`, `.dump`), архивы ZIP/7Z/RAR/TAR/GZ/BZ2/XZ/ZST/LZIP и поддерживаемые EXE-пакеты. Все контейнеры разбираются только in-process managed-кодом; приложение не запускает `tar.exe`, vendor EXE, Python или другие внешние unpacker/firmware tools. Поддерживаются вложенные контейнеры и Dell PFS EXE, которые читаются как данные. CAB/ISO больше не объявляются поддерживаемыми, пока для них не появится проверенный managed parser. Каждый найденный кандидат проходит ту же строгую UEFI/BIOS-проверку, а при нескольких корректных образах приложение просит явно выбрать нужный. Выбранный payload копируется во временное защищённое хранилище сеанса и повторно проверяется по SHA-256.
- **Системный BIOS**: приложение сначала пытается считать полный SPI flash через C610/X99 hardware sequencing. Размер SPI определяется по Intel Flash Descriptor/компонентам, чтение выполняется дважды и сверяется по области/карте регионов и SHA-256. Если Host CPU не имеет read-доступа ко всем регионам, сохраняется явно помеченный частичный SPI; если Descriptor нельзя достоверно прочитать, выполняется безопасный fallback до BIOS-региона. Временный дамп удаляется при закрытии приложения.
- При выборе нового файла предыдущий активный образ и результаты сохраняются до успешного импорта: ошибка чтения или отмена выбора BIOS внутри архива не уничтожает текущую сессию. После успешной загрузки новый образ атомарно заменяет текущий анализ. Перед новым системным SPI-дампом старый активный образ по-прежнему сбрасывается, чтобы не показывать старые сведения как результат аппаратного чтения. При ошибке чтения никакие сведения о BIOS или плате не подменяются данными текущей Windows-системы.

Аппаратный транспорт первоначально проверен 05.09.2026 на HUANANZHI X99-F8D PLUS V1.0: два чтения BIOS-региона по 8 МиБ дали одинаковый SHA-256 и корректный UEFI-анализ. Текущая реализация расширена до full-SPI-first и требует повторной аппаратной проверки полного/частичного сценария на реальной плате. Поддерживаются Haswell-E/EP или Broadwell-E/EP и C610/X99 PCH 8086:8D40/8D44/8D47. Платы с другим PCH, в том числе продаваемые как X99, требуют отдельного модуля.

Полным дампом файл называется только когда Descriptor прочитан и подтверждён, размер физического SPI выведен из component density, все отображённые регионы доступны для чтения и всё адресное пространство SPI удалось считать. Недоступные аппаратно регионы не маскируются под успешный backup: такой результат маркируется как **частичный SPI**, а недоступные диапазоны заполняются `FF` только как placeholder для анализа. Если Descriptor недоступен, приложение сохраняет только проверенный BIOS-регион и явно показывает fallback. Существующие файлы не перезаписываются.

## Интерфейс и анализ
- Рабочий процесс разделён на **Источник BIOS**, **Информация о BIOS**, **Secure Boot**, **UEFI-драйверы**, **TurboBoost Unlock**, **Персонализация** и **Сохранить**. TPM UI временно скрыт до продолжения аппаратной проверки. Страницы анализа скрыты до успешной загрузки образа. После выбора файла или создания проверенного системного дампа приложение автоматически переходит к информации об образе.
- Файл можно выбрать через системный picker или перетащить только на страницу **Источник BIOS**. Drag & Drop отключается на остальных страницах и на время чтения системного дампа; он принимает ровно один образ BIOS, архив или EXE-пакет и запускает тот же валидирующий pipeline, что и picker.
- По умолчанию язык и тема следуют Windows. В **Параметрах** можно вручную выбрать EN, RU, Українська, 中文 и System/Light/Dark; изменения применяются сразу и сохраняются в пользовательских настройках Windows.
- В боковой панели после загрузки показывается только имя текущего файла. Успешная загрузка не создаёт отдельную нижнюю плашку «образ загружен»; нижняя область появляется только для прогресса, ошибок и действительно значимых статусов.
- Имя/путь, размер, SHA-256 и тип принятого образа: UEFI, Intel SPI или поддержанная UEFI-капсула. Некорректные/неопознанные файлы отклоняются до показа результатов.
- UEFI-тома: смещения, размеры, GUID файловой системы, контрольные суммы заголовков.
- Регионы Intel Descriptor: границы, выход за файл, пересечения; учтены дополнительные Wellsburg/X99-регионы Device Expansion и Secondary BIOS.
- Текстовые маркеры AMI/Aptio/X99/производителей. Это подсказки, а не подтверждённые версия, дата или совместимость платы.
- Карточки **BIOS** и **Системная плата** работают только с текущим анализируемым firmware image — в том числе сразу после получения системного SPI-дампа. Производитель/версия/дата BIOS извлекаются из подтверждаемых данных самого образа (`BIOS Message`, `$FID`, vendor marker), а модель платы может дополняться только data-driven mapping известного BIOS ID. Windows SMBIOS/registry не используются для заполнения этих карточек. Поля, которых нет в самом образе (например, серийный номер в stock-файле), показываются как недоступные, а не выдумываются.
- На странице информации сначала показывается **Информация об образе**, затем краткий статус/предупреждения Secure Boot и структурные результаты. Подробности сертификатов вынесены на отдельную страницу Secure Boot. Сертификаты анализируются внутри обычных и LZMA-сжатых AMI FFS: SHA-256/совпадение с эталонными Microsoft-сертификатами, период действия, алгоритм подписи, тип и размер открытого ключа; для самоподписанных сертификатов проверяется криптографическая подпись. Если издатель отсутствует в образе, интерфейс явно сообщает, что подпись цепочки не проверялась.
- Отдельная страница **UEFI-драйверы** показывает полный найденный inventory активных DXE/MM FFS-файлов и отдельный блок **проверенных X99 update policies**. Поэтому количество карточек обновления намеренно меньше общего количества найденных драйверов: в update-блок попадают только компоненты, для которых известна точная политика обновления либо явное ограничение; полный список остаётся ниже в инвентаре. Анализатор рекурсивно разбирает PI sections, PE32/PE32+ и TE, поддерживает PI EFI standard compression, Tiano custom compression и AMI LZMA GUID-defined encapsulation, отмечает W+X-секции и выполняет точное GUID + SHA-256 сопоставление. Generic `UefiDriverUpdatePlanner` остаётся planning-only. Исполняемый `X99UefiDriverImageUpdater` разрешает только catalog-pinned exact source SHA-256 -> exact embedded candidate SHA-256 transitions; same-GUID/latest-version никогда не является достаточным разрешением. Для `Ready/CanApply` UI показывает кнопку **Обновить** и запускает managed update сразу без дополнительного confirmation dialog; после операции новый образ повторно анализируется и становится текущим. Физические стратегии: `InPlace`, `GrowIntoAdjacentFreeSpace` и `RebuildFirmwareVolume`; FV не изменяет размер, PAD/free-space перераспределяется по PI-правилам, обычные position-independent DXE/MM/application FFS могут сдвигаться только внутри того же FV. Pure PEIM допускается к перемещению только если strict direct PE32/PE32+ XIP rebase доказан по ImageBase/RVA/relocation table; TE, SEC/PEI core, combined PEIM/DXE, compressed/guided/nested PEI и неоднозначные relocation остаются fail-closed. После изменения unrelated FFS/TurboBoost/microcode и состояние CPU Patch `6F 06F2` обязаны сохраниться.
- Страница **TurboBoost Unlock** выполняет встроенный анализ известных Xeon E5-v3 Turbo Unlock payloads: точные SHA-256 идентичности, калиброванные PE fingerprints, прямое MSR-поведение и отдельный RAW-профиль. Сторонние утилиты и detector-процессы не запускаются. В активных RAW FFS также разбираются валидные Intel microcode. Для TurboBoost Unlock целевым считается именно Haswell-E/EP CPU Patch `6F 06F2` (`platform flags 0x6F`, CPUID `0x000306F2`); его наличие/удаление отображается и на информационной странице, и на странице TurboBoost Unlock. Если структура AMI RAW FFS и Intel FIT однозначно поддерживается, на странице TurboBoost доступна кнопка удаления; после нажатия операция начинается сразу без дополнительного диалога подтверждения и использует собственный managed C# updater: исходный FFS/FV сохраняет размер и позицию, оставшиеся microcode уплотняются внутри payload, освобождённые байты возвращаются в erase-state, Intel FIT канонически уплотняется как в эталонных MMTool-style образах: удаляется только соответствующая type-1 запись, адреса оставшихся microcode обновляются, остальные используемые FIT entries сохраняются в исходном порядке, хвост заполняется `0xFF`, а результат повторно проверяется. Операция создаёт только новый временный образ и никогда не перезаписывает исходный файл.
- Политика совместимости TurboBoost Unlock задаётся data-driven каталогом. Сейчас `retainedFamilies` пуст: `ser8989-turbohack`, `c-payne`, `dufus-v3`, `freecableguy-v3x4`, `mof-v3-mof`, `nalex-upt` и `randir-mof-powercut` являются **Foreign**, если семейство однозначно подтверждено сильным evidence; near/generic/ambiguous-кандидаты остаются `Unclassified` и автоматически не изменяются. Для подтверждённого Foreign FFS **чистый baseline BIOS не требуется**: его собственный source-bound `Ready/RemoveInjectedFfs` план позволяет индивидуальное точечное удаление. Перед записью managed executor заново читает текущий source, проверяет его SHA-256, повторно выполняет полный анализ, заново подтверждает Foreign-классификацию и exact GUID/FV/FFS offset/size/type/SHA-256, запускает низкоуровневый FFS preflight, проверяет активное `DataValid` состояние, checksum/структуру FV/FFS, erase polarity и запрет `FFS_ATTRIB_FIXED`. Затем меняется ровно один state-byte PI FFS `DataValid → Deleted`; остальные байты, FFS/FV layout, TurboBoost-модули и microcode обязаны остаться неизменными, а результат полностью анализируется повторно. UI предоставляет только индивидуальную кнопку: после нажатия операция сразу запускается без дополнительного ContentDialog; clean-BIOS picker и bulk «удалить все» для этой операции отсутствуют. Baseline сохраняется только как backend-инструмент исследования будущей ветки `RestoreBaselineFfs`: если Foreign Unlock изменил/заменил штатный FFS, topology может определить restore-intent, но копирование stock-байтов намеренно остаётся в `RequiresBaselineByteAuthorization` и UI restore-action отсутствует. Состояние CPU Patch `6F 06F2` никогда не восстанавливается из baseline.
- Страница **Персонализация** работает только с открытым образом BIOS и создаёт новую временную копию, не изменяя исходный файл. Для распознанных AMI X99 firmware она независимо находит два стартовых изображения: большой boot logo и малый AMI logo. Каждое изображение можно заменить отдельным BMP; автоматическая мутация разрешается только для несжатого `BI_RGB` с теми же шириной, высотой, ориентацией, глубиной цвета и внутренней BMP-разметкой, что у текущего изображения. FFS/LZMA секция пересобирается managed-кодом, checksum и структура FV проверяются повторно, а второе стартовое изображение обязано остаться побайтно эквивалентным по SHA-256. Персонализация не перемещает соседние FFS: код подбирает допустимое LZMA `NumFastBytes` в исходном AMI-формате без EOS. Если перепакованный FFS стал меньше на целую единицу 8-байтового выравнивания, прежняя граница allocation сохраняется стандартной RAW padding-секцией внутри только целевого FFS; созданная программой секция помечается `XV3P` и безопасно заменяется при следующей модификации. Если LZMA-данные реально не помещаются в исходный allocation, операция fail-closed завершается как нехватка безопасного места. На той же странице можно отключить или вернуть стартовый AMI BDS `ConInAvailabilityBeep`; патч ищется по структуре PE и связанным данным, а не по фиксированному смещению. Для тесного BDS сначала используются существующие в том же executable PE листовые `return EFI_SUCCESS` (`xor/sub eax,eax; ret`): начало функции переключается на относительный `jmp` к проверенному stub, после чего несколько семантически эквивалентных вариантов совместно перебираются с LZMA `NumFastBytes` без перемещения соседнего FFS. Старый inline-патч `xor eax,eax; ret` остаётся распознаваемым; обратное включение реконструирует исходный RIP-relative `lea` по уникальному `ConsoleInDevicesStartedProtocol` GUID. Диагностические POST/PEI/DXE beep-коды этой настройкой не отключаются.
- Скрытый до аппаратной валидации backend **TPM** показывает только признаки, найденные в открытом firmware image, и отдельно — последний runtime-отчёт опционального пассивного `XeonV3 TPM Debug` DXE-драйвера. Анализ образа не обращается к Windows TPM API, WMI, Registry или внешним базам. DXE-драйвер не отправляет TPM-команды, не захватывает locality и не меняет LPC/decode/strap/RCBA-регистры. Он упакован в тот же AMI X99 формат, что штатные DXE-модули (`ImageBase=0`, alignment `0x20`, AMI LZMA GUID-defined FFS), а DEPEX ждёт Variable/VariableWrite Architectural Protocol и PCI Root Bridge I/O. Версия отчёта 3 запускает диагностику на `ReadyToBoot`: перечисляет все EFI PCI root bridge, фиксирует выбранный Wellsburg LPC, делает read-only снимок RCBA/SPI, анализирует ACPI `TPM2`/`TCPA` и TPM AML-policy, а locality 0–4 читает с отдельным `EFI_STATUS` для каждого регистра. `TCG2.GetCapability` вызывается только если аппаратный TIS/PTP-интерфейс уже выглядит валидным. Reader сохраняет совместимость с отчётами v1/v2. На странице доступны source-bound установка и удаление только этого FFS-драйвера с повторной полной проверкой образа; прямая прошивка дополнительно блокируется, если в образе найден старый или побайтно неизвестный вариант debug-драйвера.
- Для распознанной X99/AMI-разметки команда **Исправить Secure Boot** сначала немедленно показывает индикатор операции, а тяжёлый managed preflight/перестроение/повторный анализ выполняет вне UI-thread; команда создаёт временный исправленный образ: удаляет устаревшие Microsoft 2011 и небезопасные ключи из управляемых PK/KEK/db, добавляет Microsoft KEK 2K CA 2023, Microsoft Option ROM UEFI CA 2023, Microsoft UEFI CA 2023 и Windows UEFI CA 2023. Небезопасные ключи определяются не только по каталогу известных SHA-256: инспектор также распознаёт явные test/debug/development/`DO NOT TRUST` маркеры и самоподписанные CA code-signing ключи загрузчиков вроде GRUB; слабые/просроченные неизвестные OEM-ключи сами по себе не удаляются автоматически. Если после удаления небезопасного PK хранилище Platform Key остаётся пустым, для этого образа создаётся новый сильный самоподписанный Platform Key; закрытый ключ используется только при создании сертификата и не сохраняется. Уже существующий сильный нетестовый PK сохраняется. Остальные OEM/неизвестные сертификаты в KEK/db сохраняются. После каждой стадии образ заново проходит структурную и сертификатную проверку. Исходник и работающая система не меняются; временный образ удаляется при закрытии приложения; прошивка не запускается.
- Одновременно работает только один экземпляр приложения. Single-instance регистрация выполняется до инициализации XAML; повторный запуск перенаправляет активацию в основной процесс, разрешает ему вернуть foreground и показывает локализованное уведомление. Предупреждения, статусы и данные анализа можно выделить и скопировать. Интерфейс использует адаптивный WinUI NavigationView: на широком окне видна полная панель, на среднем — компактная, на узком — минимальная; основные карточки перестраиваются в одну колонку.
- Асинхронная загрузка, прогресс и отмена. Для принимаемых BIOS-образов применяется диапазон 1–128 МиБ; структурный анализ также проверяет стандартный UEFI FFS GUID, checksum и block map firmware volume.
- Капсулы не распаковываются для прошивки. Подпись капсулы и плата назначения пока не проверяются; Intel microcode в активных RAW FFS проверяются отдельно на странице TurboBoost Unlock.
- Структурный анализ не подтверждает пригодность к записи.

Заголовки томов, FFS-типы и section-коды проверяются по [UEFI PI 1.10](https://uefi.org/specs/PI/1.10/V3_Code_Definitions.html). В первом этапе это структурный анализ, не полный UEFI-парсер.

## Сборка
Нужны Windows x64, .NET SDK 10.0.400 (или совместимый из global.json) и сеть для первого восстановления NuGet. WDK и сертификат подписи драйвера не нужны.

~~~powershell
.\scripts\Build-Release.ps1
~~~

Результат: **publish\XeonV3Control2.exe** — один самодостаточный EXE с .NET, Windows App SDK и неизменённым ThrottleStop_x64.sys внутри. При запуске WinUI/.NET распаковывают runtime; внешний установщик Windows App Runtime не требуется. Single-file bundle публикуется со встроенным сжатием (`EnableCompressionInSingleFile=true`) и без ReadyToRun (`PublishReadyToRun=false`), чтобы не раздувать portable EXE. Trimming намеренно выключен: для WinUI/XAML релиз важнее держать fail-safe, чем экономить размер агрессивным удалением кода.

`Build-Release.ps1` после publish выводит фактический размер EXE и SHA-256. Допустимый максимум централизован в `XeonV3Control.App.csproj` через `ReleaseMaximumExecutableMiB` (сейчас 384 MiB); превышение лимита останавливает релиз до замены последней рабочей версии. Это защищает от случайного возврата к ~0.5 GiB артефакту.

Версии NuGet-пакетов централизованы в `Directory.Packages.props`. Схема single-file сохраняет unpackaged/self-contained WinUI-модель: `EnableMsixTooling`, `IncludeAllContentForSelfExtract`, `PublishSingleFile` и `WindowsAppSDKSelfContained` остаются включены.

Приложение всегда запрашивает права администратора через манифест. Анализ файла драйвер не загружает. Перед регистрацией системного драйвера во время выполнения проверяются точный SHA-256 встроенного бинарника и Authenticode через Windows; Authenticode проверяется по уже открытому заблокированному handle этого же файла, а release-сборка дополнительно фиксирует SHA-256 сертификата подписанта TechPowerUp. Извлечённый файл удерживается открытым без разрешения записи/удаления до остановки сервиса. Выбор файла использует Windows App SDK 1.8 pickers, включая повышенный процесс.

Открыть файл из командной строки:
~~~powershell
.\publish\XeonV3Control2.exe "<path-to-BIOS-image-or-package>"
~~~

## Архитектура
- src/XeonV3Control.Core — общий загрузчик, структурный анализ, локализация, проверка дампа, TPM firmware-анализ, fail-closed SPI read/write sequencer и managed UEFI image mutations.
- src/XeonV3Control.App — WinUI shell, picker/Drag & Drop, параметры языка и темы, временные образы, TPM boot-report reader и строго ограниченный транспорт ThrottleStop.
- tests — тесты анализатора, дампов, локализации, обновления Secure Boot и эмулятора SPI.
- third_party/ThrottleStop — исходный выбранный бинарник и provenance.
- docs/DRIVER-RESEARCH.md — исследование, ABI драйвера, варианты FPT/AFU/CHIPSEC, границы проверки.

Прямая запись BIOS доступна только по явной команде на странице **Сохранить** и после отдельного подтверждения. Она использует уже встроенный `ThrottleStop_x64.sys`, записывает только BIOS region и никогда не пишет Descriptor/ME/GbE/PDR и не снимает защиты. Перед первым erase заново проверяются платформа, FRAP/PR0–PR4, размер block erase и совместимость текущего/целевого BIOS. `FLOCKDN=0` сам по себе не блокирует X99-плату: приложение делает снимок FRAP/PR0–PR4 и перепроверяет его перед каждым erase; если конфигурация изменится после начала сектора, сектор сначала дописывается и проверяется, а операция останавливается до следующего erase. Изменяются только отличающиеся 4 КиБ секторы, а в конце сверяется SHA-256 всего BIOS region. Реальная аппаратная прошивка всё равно требует отдельной проверки на поддерживаемой X99/C610 плате.

## Проверки
~~~powershell
dotnet test .\tests\XeonV3Control.Tests\XeonV3Control.Tests.csproj -c Release
.\scripts\Test-UI.ps1 -Image "<known-valid-BIOS-image>"
~~~

Test-UI запускает именно EXE, проверяет скрытие image-only навигации до загрузки, открывает файл, проверяет страницы BIOS/Secure Boot/UEFI-драйверы/TurboBoost Unlock/Персонализация/Сохранить/Параметры, подтверждает скрытый TPM UI и reset-state, а также сохраняет PNG пустого/заполненного экрана и узкого/среднего responsive-layout для четырёх языков. Это внутренняя проверка рендеринга: нативные диалоги выбора файла и UAC в неё не входят. Она никогда не читает физическую плату.

Обычный диагностический лог и временные BIOS-образы хранятся только в защищённом каталоге текущего сеанса под Windows CommonApplicationData (`ProgramData`). Каталог создаётся сразу с закрытым DACL для `SYSTEM` и локальных администраторов, удерживается от подмены на протяжении сеанса и удаляется при нормальном закрытии; неактивные каталоги аварийно завершённых сеансов очищаются при следующем запуске. При необработанном падении `error.txt` сначала создаётся рядом с исполняемым `XeonV3Control2.exe`, а если каталог приложения недоступен для записи — используется защищённый transient-root. При отказе загрузки драйвера дополнительно проверяются системные события Code Integrity. Приложение не меняет настройки защиты Windows.
